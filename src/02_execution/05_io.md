# 执行器与系统 IO

在前面关于 [`Future` trait](./02_future.md) 的章节中，我们讨论过这个对一个 socket 执行异步读取的 future 示例：

```rust,ignore
{{#include ../../examples/02_02_future_trait/src/lib.rs:socket_read}}
```

这个 future 会读取 socket 上的可用数据；如果没有可用数据，它就会向执行器让出控制权，请求在 socket 再次变为可读时唤醒它的任务。然而，从这个例子中看不出 `Socket` 类型是如何实现的，尤其是 `set_readable_callback` 函数的工作方式并不明显。我们怎样才能安排在 socket 变为可读时调用 `wake()` 呢？一种选择是让一个线程不断地检查 `socket` 是否可读，并在合适的时候调用 `wake()`。然而，这种做法效率很低，因为每个被阻塞的 IO future 都需要一个单独的线程。这会大大降低我们异步代码的效率。

在实践中，这个问题是通过与具备 IO 感知能力的系统阻塞原语集成来解决的，例如 Linux 上的 `epoll`、FreeBSD 和 Mac OS 上的 `kqueue`、Windows 上的 IOCP，以及 Fuchsia 上的 `port`（它们都通过跨平台的 Rust crate [`mio`](https://github.com/tokio-rs/mio) 暴露出来）。这些原语都允许一个线程阻塞在多个异步 IO 事件上，一旦其中某个事件完成就返回。在实践中，这些 API 通常看起来像这样：

```rust,ignore
struct IoBlocker {
    /* ... */
}

struct Event {
    // 唯一标识所发生且被监听的事件的 ID。
    id: usize,

    // 等待的信号集合，或已发生的信号集合。
    signals: Signals,
}

impl IoBlocker {
    /// 创建一个新的、要阻塞等待的异步 IO 事件集合。
    fn new() -> Self { /* ... */ }

    /// 表达对某个特定 IO 事件的关注。
    fn add_io_event_interest(
        &self,

        /// 事件将要发生的对象
        io_object: &IoObject,

        /// 一组可能出现在 `io_object` 上的信号，事件应
        /// 针对这些信号触发，同时配有一个 ID，
        /// 赋给由该关注产生的事件。
        event: Event,
    ) { /* ... */ }

    /// 阻塞，直到其中一个事件发生。
    fn block(&self) -> Event { /* ... */ }
}

let mut io_blocker = IoBlocker::new();
io_blocker.add_io_event_interest(
    &socket_1,
    Event { id: 1, signals: READABLE },
);
io_blocker.add_io_event_interest(
    &socket_2,
    Event { id: 2, signals: READABLE | WRITABLE },
);
let event = io_blocker.block();

// 例如，如果 socket 1 变为可读，就打印 "Socket 1 is now READABLE"。
println!("Socket {:?} is now {:?}", event.id, event.signals);
```

future 执行器可以利用这些原语来提供异步 IO 对象（例如 socket），这些对象可以配置回调，以便在特定 IO 事件发生时运行。以上面 `SocketRead` 的例子来说， `Socket::set_readable_callback` 函数可能大致如下面的伪代码所示：

```rust,ignore
impl Socket {
    fn set_readable_callback(&self, waker: Waker) {
        // `local_executor` 是对本地执行器的引用。
        // 本可以在创建 socket 时提供它，但实践中为了方便，
        // 许多执行器实现都通过线程局部存储
        // 把它传递下来。
        let local_executor = self.local_executor;

        // 这个 IO 对象的唯一 ID。
        let id = self.id;

        // 把本地 waker 存入执行器的映射表，以便
        // IO 事件到达时可以调用它。
        local_executor.event_map.insert(id, waker);
        local_executor.add_io_event_interest(
            &self.socket_file_descriptor,
            Event { id, signals: READABLE },
        );
    }
}
```

这样，我们就可以只用一个执行器线程，它能够接收任意 IO 事件，并将其分发给相应
的 `Waker`，由 `Waker` 唤醒对应的任务，从而让执行器在返回去检查更多 IO 事件
之前驱动更多任务至完成（如此循环往复……）。
